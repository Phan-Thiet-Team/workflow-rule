QUY TRÌNH / TASK & GIT

Quy trình làm việc của team

Tài liệu mô tả quy trình quản lý task và quy trình làm việc với Git của team trên GitHub.

Không tìm thấy mục phù hợp. Thử một từ khóa khác.
MỤC 01

1. Quy trình quản lý task

1.1. Các trạng thái

Trạng tháiÝ nghĩaNgười chuyển
BacklogTask mới được tạo, chưa reviewPM / QC
TodoPM đã duyệt, sẽ làmPM
UndoPM không duyệt, không làmPM
In ProgressĐang thực hiệnNgười được assign
QC ReviewĐã làm xong, chờ QC kiểm traNgười được assign
Ready for UATQC đã kiểm tra xong, đã đưa lên UATQC
Ready for PRODUAT đã nghiệm thu, chờ đưa lên productionQC / PM
DoneĐã đưa lên productionPM / DevOps
CancelledTask bị hủy khi đang làmPM

1.2. Luồng trạng thái

                       ┌──> Undo
Backlog ──(PM review)──┤
                       └──> Todo ──> In Progress ──> QC Review ──> Ready for UAT ──> Ready for PROD ──> Done
                                          │
                                          └──> Cancelled (task bị hủy khi đang làm)

1.3. Chi tiết từng bước

  1. Tạo task
    • PM tạo task khi khách hàng yêu cầu chức năng mới.
    • QC tạo task khi PM yêu cầu.
    • Task mới tạo ở trạng thái Backlog.
  2. Review task: PM review task.
    • Duyệt và sẽ làm: chuyển sang Todo.
    • Không duyệt: chuyển sang Undo.
  3. Assign: PM assign task cho người phù hợp (QC, Dev hoặc DevOps) tùy loại task.
  4. Estimate: người được assign ước lượng thời gian làm và trao đổi với PM.
  5. Set deadline: PM chốt deadline sau khi thống nhất estimate.
  6. Thực hiện: khi bắt đầu làm, người được assign kéo task sang In Progress.
  7. Hoàn thành: làm xong, kéo task sang QC Review, tag QC vào task và báo trong nhóm.
  8. QC kiểm tra: QC kiểm tra xong thì đưa lên môi trường UAT và kéo task sang Ready for UAT.
  9. Nghiệm thu UAT: UAT đạt thì kéo task sang Ready for PROD.
  10. Production: sau khi đã đưa lên production, chuyển task sang Done.
Nếu task bị hủy khi đang làm, PM chuyển task sang Cancelled.

MỤC 04

4. Quy tắc Pull Request và merge

Trên GitHub, Merge Request (MR) được gọi là Pull Request (PR).
  1. Không merge trực tiếp từ local vào develop, uat, master. Tất cả phải thông qua PR.
  2. Không push trực tiếp lên các nhánh môi trường. Chỉ được đưa code vào qua PR, trừ tài khoản hoặc quy trình khẩn cấp đã được ủy quyền rõ ràng.
  3. Nội dung PR bắt buộc có:
    • Mã task
    • Mô tả thay đổi
    • Kết quả kiểm thử
  4. Review: phải có ít nhất 1 người review và approve trước khi merge. Với thay đổi quan trọng, nên yêu cầu Lead hoặc người phụ trách module phê duyệt.
  5. Trước khi merge: phải xử lý hết conflict và các comment review còn tồn đọng.
  6. Chất lượng code:
    • Không merge code chưa hoàn thành hoặc chưa được kiểm thử vào develop.
    • Không đưa code chưa được nghiệm thu vào master.
  7. Sau khi merge thành công: xóa branch nguồn nếu không còn dùng nữa.

MỤC 05

5. Quy tắc xử lý conflict

  1. Người tạo branch chịu trách nhiệm xử lý conflict trên branch của mình.
  2. Không tự ý ghi đè code của người khác khi chưa hiểu rõ thay đổi đó.
  3. Không giải quyết conflict trực tiếp trên develop, uat hoặc master.
  4. Cách xử lý: checkout về branch đang làm, cập nhật nhánh đích mới nhất, rồi merge nhánh đích vào branch công việc để xử lý conflict.
  5. Sau khi xử lý conflict: kiểm tra lại code, chạy test và bảo đảm pipeline pass trước khi merge.
  6. Conflict liên quan nghiệp vụ hoặc logic của người khác: phải trao đổi với tác giả code hoặc Lead trước khi quyết định giữ thay đổi nào.

Các lệnh xử lý conflict

Terminal
# 1. Chuyển về branch công việc
git checkout feat/PRJ-123

# 2. Cập nhật nhánh đích mới nhất
git fetch origin

# 3. Merge nhánh đích vào branch công việc
git merge origin/develop

# 4. Sửa các file bị conflict, rồi đánh dấu đã xử lý
git add <file-đã-sửa>
git commit

# 5. Chạy test, rồi push lên lại
git push origin feat/PRJ-123

MỤC 07

7. Phương án đưa từng chức năng lên môi trường Đề xuất

Phần này là đề xuất, chưa áp dụng. Mục tiêu: thay vì đưa nguyên develop lên uat rồi master theo từng đợt, team có thể chọn những chức năng muốn đưa lên. Khi chốt phương án, cần sửa lại mục 2.2, mục 5 và mục 6 cho khớp.

Cách 1: Đưa từng feature branch lên từng môi trường

Mỗi feature branch có PR riêng vào lần lượt develop, uat, master. Chức năng nào sẵn sàng thì lên chức năng đó.

master ──┬──────────────────────────────> master
         │                                  ▲
         └─ feat/PRJ-123 ──PR──> develop    │
                         ──PR──> uat        │
                         ──PR───────────────┘

Bắt buộc:

  • Feature branch phải checkout từ master, không checkout từ develop. Checkout từ develop thì branch sẽ kéo theo code của người khác chưa được nghiệm thu.
  • Không bao giờ merge develop hay uat vào feature branch. Lý do giống ở trên.
  • Nếu PR vào uat bị conflict: tạo một branch tạm từ feature branch (ví dụ conflict/PRJ-123-uat), merge uat vào branch tạm để xử lý, rồi tạo PR từ branch tạm vào uat. Feature branch gốc giữ nguyên.
  • Sau mỗi đợt release, đồng bộ lại develop và uat theo master để các nhánh không lệch nhau dần.
Ưu điểm
Chọn chức năng rất linh hoạt. Mỗi PR chỉ chứa đúng một chức năng nên review và rollback đều dễ.
Nhược điểm
Cùng một conflict có thể phải xử lý tới 3 lần, mỗi nhánh môi trường một lần. Mỗi feature tốn 3 PR.

Cách 2: Release branch và cherry-pick

Feature vẫn merge vào develop như hiện tại. Tới lúc release thì tạo một branch riêng và chỉ lấy những chức năng muốn đưa lên.

develop:  A(PRJ-123) ── B(PRJ-124) ── C(PRJ-125)
                │                        │
master ── release/2026-10-21 ◄── cherry-pick A, C
                │
                ├──PR──> uat ──(UAT đạt)
                └──PR──> master

Bắt buộc:

  • PR vào develop dùng Squash merge, để mỗi chức năng chỉ là 1 commit, tiêu đề có mã task (ví dụ feat(PRJ-123): ...).
  • Tạo release/<ngày> từ master, rồi git cherry-pick <commit> từng chức năng được chọn.
  • Nếu chức năng B phụ thuộc chức năng A thì phải cherry-pick cả A. Người lên danh sách release phải kiểm tra điều này.
Ưu điểm
Gần với quy trình hiện tại nhất, dev gần như không phải đổi thói quen. Đợt nào cần lên hết thì vẫn promote nguyên develop như cũ được.
Nhược điểm
Cherry-pick tạo commit mới với hash khác, lâu dần develop và master dễ lệch nhau và sinh conflict. Cần người theo dõi commit nào thuộc task nào, đã lên đâu.

So sánh nhanh

Cách 1: Feature branchCách 2: Cherry-pick
Hợp khiThường xuyên chọn lọc, các chức năng độc lập nhauPhần lớn lên theo đợt, chỉ thỉnh thoảng loại bớt chức năng
Thay đổi so với hiện tạiNhiều: đổi nhánh gốc, đổi quy tắc xử lý conflictÍt: thêm squash merge và release branch
Rủi ro chínhXử lý conflict lặp lại nhiều lầnPhụ thuộc giữa các commit, nhánh bị lệch nhau
Ngoài hai cách trên còn có feature flag: vẫn merge hết như cũ, nhưng bật hoặc tắt chức năng bằng cấu hình. Cách này cần sửa code để hỗ trợ.
